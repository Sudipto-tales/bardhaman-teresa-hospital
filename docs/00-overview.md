# Teresa Memorial Hospital — Admin Panel

## Why this exists

The public site is entirely static. Every value a hospital administrator would
realistically want to change is compiled into source files:

| What | Where it lives today |
|---|---|
| Phone `+91 90460 05557` | Hardcoded in all 20 `.html` files, ~4 occurrences each |
| Email `tmh.bdn@gmail.com` | Same |
| Doctor roster | `tools/site-data.mjs` → `DOCS`, `ROSTER` |
| Departments (12 pages worth) | `tools/site-data.mjs` → `DEPARTMENTS` |
| Blog posts | `tools/site-data.mjs` → `POSTS` |
| Facilities, values, milestones, testimonials | `tools/site-data.mjs` |
| Job vacancies | `html/assets/jobs.js` → `window.TMH_JOBS` |
| FAQ, lab tests, home-page counters | Inline in `website.html` |

Changing a phone number is a repo-wide find-and-replace followed by a rebuild.
That is not a workflow a hospital can own.

The panel replaces this with a database-backed CMS where every one of the values
above is a record with an owner screen.

## Phase boundaries

**Phase 1 — Design (this repo, `html/admin/`) — CURRENT**

Clickable, self-contained HTML mockups of every admin screen. No server, no
database. Mock data seeds from `assets/data/*.json` into `localStorage`, so
create / edit / delete genuinely persist across a page reload and the whole flow
can be walked end to end in a browser.

Purpose: validate information architecture, screen inventory and interaction flow
*before* a line of backend is written. Wrong screens are cheap to fix here and
expensive to fix later.

**Phase 2 — Backend**

Stack decided: **PHP on the Vayu framework**, SQLite in development, MySQL in
production. `assets/js/core/store.js` is the single seam: it is deleted and
replaced with `fetch` calls against the endpoints in
[`07-api-contract.md`](07-api-contract.md). No page JS changes.

**Phase 3 — Site migration**

`tools/site-data.mjs` and `html/assets/jobs.js` stop being source of truth. Public
pages either fetch JSON at runtime or are regenerated by `tools/build-pages.mjs`
from the database. Decided in Phase 2.

**Phase 4 — Cutover**

Seed the database from the current `site-data.mjs` content, verify byte-for-byte
that the rendered site is unchanged, then switch.

## What "done" means for Phase 1

- All 43 screens exist and are reachable from the sidebar. No dead links.
- The doctors module works end to end: add → toast → row appears → reload →
  persists → edit → delete → confirm → toast with Undo.
- Every other module renders real mock data with the same list/form pattern.
- Every constant exported from `tools/site-data.mjs` and `html/assets/jobs.js` maps to
  exactly one admin screen — see [`02-content-model.md`](02-content-model.md).

## Non-goals for Phase 1

- Real authentication (login screen is visual only)
- File uploads to disk (uploader stores data URLs in localStorage)
- Live preview of the public site
- Role enforcement (roles are displayed, not checked)
- Any change to the existing public site files or the `html/index.html` / `html/app.js`
  mockup — those stay untouched
