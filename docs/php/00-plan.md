# Teresa Memorial Hospital — admin scope fix + HTML → Vayu PHP conversion

## Context

The repo holds a finished static site (20 pages, generated by `tools/build-pages.mjs`
from `tools/site-data.mjs`) and a finished 42-screen admin design prototype
(`html/admin/`, rendered entirely in JS against a `localStorage` mock in
`assets/js/core/store.js`). Nothing has a backend.

Three things must happen:

1. **Trim the over-engineered parts of the admin design.** Appointments were
   designed as a bookable workflow; in reality the site has no booking — an
   "appointment" click just goes to the contact page for a given doctor, and some
   doctors cannot be booked at all. Job applications were designed with a hiring
   pipeline; in reality they are only submitted, mailed to HR with the CV
   attached, and archived.
2. **Add two site widgets** the panel must control: a cookie consent bar
   (on/off) and a first-visit ads popup.
3. **Convert the static HTML to PHP** on the Vayu framework
   (`/home/weloin/Projects/vayu`), SQLite in dev, MySQL in production, with the
   pages decomposed into reusable components.

Decisions taken (from the clarification round):

| Decision | Choice |
|---|---|
| Admin rendering | Thin PHP shell per screen; the existing JS core stays. `store.js` → `api.js` (fetch). |
| Auth | Real session login, multiple users, roles shown but **not** enforced. |
| Repo layout | Vayu copied into this repo at root; `html/` kept as frozen design reference. |
| Ads popup | Single record: enabled, title, image, link, start/end, frequency. |

Outcome: one repo, `design/html` holding the signed-off prototype, `development`
holding a working PHP app whose admin panel drives the public site from a
database.

## Phase 2 — Vayu scaffold and framework patches

Copy `/home/weloin/Projects/vayu` into the repo root (excluding `.git`,
`vendor/`, `database/database.sqlite`, `.env`). `composer install`.

Vayu is small and mostly right, but the conversion needs these gaps closed.
Each is a small, documented core change recorded in `docs/php/01-vayu-notes.md`:

| # | Gap | Fix |
|---|---|---|
| 2.1 | Frontend routes are an exact-match map — no `{param}` support, so `/departments/cardiology` and `/blog/{slug}` are impossible. | Patch `core/RouteManager::dispatch()` to reuse the existing `{param}` regex path (already written for API routes) for frontend routes, and pass params via a `setRouteParams()` call on `BaseController`. |
| 2.2 | 404 loads `resources/views/404.php`, which does not exist. | Add a `'404'` route key convention; fall back to a real error page. |
| 2.3 | `core/Mailer.php` has hardcoded Gmail credentials and no attachment support. | Read SMTP from `env()` (falling back to the `settings.integrations` row), add `$attachments[]` and `$replyTo` params, add `Mailer::sendTo(array $recipients, …)`. |
| 2.4 | No CSRF. | New `core/Csrf.php`: `token()`, `field()`, `verify()`. Enforced on all admin writes and public form posts. |
| 2.5 | No upload handling. | New `core/Upload.php`: extension + MIME + size validation, randomised filename, writes to `storage/uploads/<yyyy>/<mm>/` for media and `storage/cv/` for CVs (CVs never web-reachable; served by an authed streaming route). |
| 2.6 | `config/migrate.php` references an undefined `$base_url` and there is no CLI command. | Fix the bootstrap, add `migrate` / `migrate:fresh` / `seed` to `core/Console/` and the `vayu` CLI. |
| 2.7 | Migrations are raw SQLite DDL; production is MySQL. | Add dialect helpers to the `Migration` base (`id()`, `text()`, `timestamps()`, `createTable()`), so every migration is written once and runs on both. |
| 2.8 | `core/Auth.php` requires email verification and uses a fragile relative `require`. | Fix the require path; add `emailVerify` bypass for admin-created users; add `Auth::user()` and a `requireAuth()` guard used by the admin controller. |
| 2.9 | No rate limiting on public intake. | New `core/RateLimit.php` backed by a `rate_limits` table — per-IP, per-endpoint. |
| 2.10 | `config/config.php` reads `$_SERVER['HTTP_HOST']` unguarded (fatal under CLI). | Guard it. |

`.env` keys added: `MAIL_*`, `CAREERS_EMAIL`, `UPLOAD_MAX_MB`, `APP_TIMEZONE`.

## Phase 3 — Database

Schema lifted directly from `docs/02-content-model.md`, one migration file per
table in `database/migrations/`:

`settings` (key/group/value JSON), `users`, `roles`, `media`, `doctors`,
`doctor_schedules`, `leadership`, `departments`, `department_doctors`,
`facilities`, `lab_tests`, `posts`, `categories`, `post_tags`, `testimonials`,
`faqs`, `pages` + `page_sections`, `counters`, `nav_items`, `redirects`,
`seo_meta`, `jobs`, `applications`, `enquiries`, `appointments` (kept, read-only),
`popups`, `activity_log`, `rate_limits`, `migrations`.

Conventions: string ids/slugs as the public key with an integer PK,
`status`/`order`/`created_at`/`updated_at`/`deleted_at` on every content table,
repeaters stored as JSON columns where they are edit-only structures (schedules,
chips, procedures) and as real tables where they are queried (department↔doctor).

Doctor gains `appointment_enabled` (Phase 0.1).

**Seeding without retyping content:** a Node step exports the existing
JS sources to JSON, then a PHP seeder loads them:

```
tools/seed-export.mjs   imports tools/site-data.mjs + html/assets/jobs.js
                        + html/admin/assets/data/*.js
                     →  database/seeds/*.json
php vayu seed        →  rows in SQLite
```

## Phase 4 — API layer

**One generic resource controller, not twenty.** `config/resources.php` is a
registry describing each of the 20 CRUD resources — table, public id field,
writable fields with types/casts, filters, sort whitelist, required-for-publish
rules, dependency checks. `api/controllers/ResourceController.php` reads it and
implements the whole contract in `docs/07-api-contract.md`:

```
GET|POST   api/{resource}
GET|PATCH|DELETE  api/{resource}/{id}
POST       api/{resource}/reorder | bulk | {id}/restore
```

Gateway routes are literal-first, so specific endpoints still win over the
wildcard. Purpose-built controllers only where the shape differs:

| Controller | Endpoints |
|---|---|
| `AuthController` | `login`, `logout`, `me`, `forgot`, `reset` — session cookie + CSRF, not JWT |
| `SettingsController` | `GET api/settings`, `PATCH api/settings/{group}`, `test-smtp` |
| `MediaController` | upload (multipart), patch, delete-with-`usedBy`, usage |
| `PageController` | pages + section reorder |
| `PopupController` | cookie bar + ads popup config |
| `PublicIntakeController` | `api/public/enquiry`, `api/public/application` (multipart + CV) |
| `DashboardController` | summary tiles, attention list, recent feed |
| `ApplicationController` | stage/rating patch + `GET api/applications/{id}/cv` (authed file stream) |

**Deliberately absent:** any appointment write endpoint. `appointments` is
read-only — a list endpoint only, so the existing screen renders.

Every mutation writes an `activity_log` row. Responses use the envelope and error
codes already specified in `docs/07-api-contract.md`, so the panel's error
handling needs no changes.

## Phase 5 — Admin panel on PHP

The panel keeps its JS. Only two things change:

1. **`app/page/admin/<screen>.php`** — a thin shell per screen, the PHP twin of
   what `html/admin/tools/scaffold.mjs` already generates. Built from
   `app/components/admin/{head,sidebar,topbar,scripts}.php` so the 43 shells are
   one component call each, not 45 lines of copy-paste. A PHP port of
   `scaffold.mjs` generates them from the same page table.
2. **`assets/admin/js/core/api.js` replaces `store.js`** — same method names,
   same promise shapes, `fetch` against `/api/*` with the CSRF header. Seed files
   (`assets/data/*.js`) are dropped. Per the design docs this is the only
   client-side change; no page JS is touched.

Routing: `/admin`, `/admin/{screen}`, `/admin/{screen}/{id}` via the Phase 2.1
patch. `AdminController` guards every route with `Auth::isAuthenticated()` and
renders the shell. `/admin/login` and `/admin/forgot-password` are chrome-less.

## Phase 6 — Public site as components

Component tree under `app/components/site/` mirrors the generator functions that
already exist in `tools/build-pages.mjs` — that file is the proof these are the
right seams:

```
layout/    head · brand-rail · nav-bar · mega-menu · header · mobile-dock
           scroll-spy · prefooter · footer · scripts
block/     banner · post-banner · stats · intro · cards · conditions · team
           cta · purpose · mosaic · related
card/      doctor · blog · facility · job · testimonial · lab-test
form/      enquiry · application · field (input/select/textarea/file)
widget/    cookie-bar · ads-popup · faq-accordion · counter
```

Pages in `app/page/site/`, one per public template, composed only of the above:

| Route | Page | Replaces |
|---|---|---|
| `/` | `home.php` | `website.html` |
| `/about` `/doctors` `/facilities` `/contact` `/careers` `/departments` `/lab-diagnostics` | one file each | same-named `.html` |
| `/departments/{slug}` | `department.php` | the 12 generated department pages |
| `/blog` · `/blog/{slug}` | `blog.php` · `blog-post.php` | `blog.html`, `blog-post.html` |
| `/careers/{slug}` | `job.php` | `job.html?id=` |

Controllers read published rows through a thin `app/models/` layer (plain
functions over `db_fetch_all`), never touching `site-data.mjs` again. Old
`*.html` paths get 301s from the `redirects` table. Settings (phone, email,
address, social, theme colours) resolve from the `settings` table — the
find-and-replace problem the whole panel exists to kill.

CSS/JS move to `assets/site/` unchanged; only the paths they are referenced by
change (`base_url()`).

## Phase 7 — Forms, mail and popups

**Enquiry** (`contact` page) → `POST /api/public/enquiry` → row in `enquiries` +
notification mail to `settings.integrations.notifyEnquiryTo`. Honeypot +
rate limit + CSRF.

**Job application** (`/careers/{slug}`) → `POST /api/public/application`,
multipart:
1. Validate fields + CV (pdf/doc/docx, ≤ `UPLOAD_MAX_MB`).
2. Store CV under `storage/cv/` with a randomised name; row in `applications`.
3. Mail HR (`settings` careers address, `job.applyEmail` overriding it) with the
   full applicant detail table **and the CV attached** — the Phase 2.3 Mailer
   change exists for this.
4. Send the applicant a plain acknowledgement.
5. Failures to mail do not lose the row: the row is written first, mail is
   attempted after, and a failed send is flagged on the record and retried from
   the panel.

**Appointments**: no endpoint. The contact page keeps its request form as an
*enquiry* of source `appointment`, and the "Book appointment" link from a doctor
card carries `?doctor=<slug>` to preselect. Doctors with
`appointment_enabled = 0` render no link at all.

**Cookie bar**: rendered from `popups.cookie` when enabled; consent stored in a
first-party cookie for 180 days; suppressed on repeat visits.

**Ads popup**: rendered from `popups.ads` when enabled and inside its date
window; shown on first visit per the configured frequency (`session` or
`days:N`), tracked in a first-party cookie; dismissible, focus-trapped,
`prefers-reduced-motion` respected.

## Phase 8 — Hardening and handover

Password hashing (bcrypt), session cookie flags, CSRF on every write, prepared
statements everywhere (already the Vayu default), upload MIME allowlist, CVs
outside the web root, `.htaccess` deny on `storage/` and `database/`, error
display off when `APP_DEBUG=false`, MySQL switch verified by running the full
migration + seed against MySQL with only `.env` changed.

## Verification

**Phase 1**: re-run `node tools/build-pages.mjs`; `git diff` must be empty apart
from the path move. Open `html/website.html` and `html/admin/dashboard.html` from
disk — both must render exactly as before.

**Phase 3**: `php vayu migrate && php vayu seed`, then
`sqlite3 database/database.sqlite "select count(*) from doctors"` etc. against the
counts in `site-data.mjs`.

**Phase 4**: `curl` each verb of one resource — list, create, patch, delete,
restore, reorder, bulk — plus a 422 (missing required), a 409 (duplicate slug), a
401 (no session) and a 409 `HAS_DEPENDENTS` (delete a department that has doctors).

**Phase 5**: walk the end-to-end loop the design docs define as "done" — add a
doctor → toast → row appears → reload → persists → edit → delete → confirm →
Undo — now against SQLite. Repeat in a second browser as a second user.

**Phase 6**: every public route returns 200 and renders; diff the PHP-rendered
home page against `html/website.html` to catch dropped markup; check both themes
and 1280 / 1024 / 768 / 390 widths.

**Phase 7**: submit a real application with a PDF — assert the row exists, the CV
is on disk and not reachable over HTTP, HR receives the mail with the attachment,
and the panel's Download CV streams it. Toggle the cookie bar and the ads popup
from the panel and reload the site to confirm both obey.

**Phase 8**: switch `.env` to MySQL, re-run migrate + seed, re-run the Phase 4 and
6 checks unchanged.
